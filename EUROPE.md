# Pokémon Pinball: Ruby & Sapphire — European version (BPPP)

The `europe` branch extends the pret disassembly of Pokémon Pinball: Ruby & Sapphire to the
multi-language European release (English, French, German, Italian and Spanish). The same source
tree builds both games:

| ROM | Game code | SHA1 |
|---|---|---|
| `pokepinballrs.gba` | BPPE (USA) | `9fec81ce2c5df589e0371a0bf2f92a5fe8db730b` |
| `pokepinballrs_eu.gba` | BPPP (Europe) | `b8b7881eaa9856b5ada99078ad1053d31cb79827` |

## Status

- **Both ROMs are rebuilt byte for byte.** Every European change is inside `#ifdef EUROPE`, so
  the US build is unchanged.
- **Code: all 848 functions of the European build are C.** None of them falls back to the
  original assembly. One of them relies on a fake match (see *Matching notes*), like one that
  already exists in the US code.
- **Data: the European data is in source form.** Graphics are PNG/palette files, texts and
  tables are assembler source, and pointers are symbolic. Of about 9.4 MB of read-only data, only
  686 bytes are still anonymous `.byte` lines (small tables in `rom_2`). The ROM also has a
  16 KB block at `0x08FE0000` that the game never references, kept as bytes (see *Remaining work*).

## Building

Set up the toolchain as described in [INSTALL.md](INSTALL.md), then:

    make compare_eu     # European ROM (same as: make REGION=EU compare)
    make compare        # US ROM

The build does not need the original ROM. The porting tools in `tools/eu_port` do: copy the
European ROM to `baserom_eu.gba` at the root of the repository (it is ignored by git), or set
`BASEROM_EU`.

On Windows (MSYS2), use the msys `jq`, because the mingw one writes CRLF line endings. Also run
Python in UTF-8 mode (`python -X utf8`).

## What the European version changes

These are the differences found while porting:

- **Language selection.** A language selection screen appears at the first boot. The language
  is stored in the save data: `gMain_saveData.language`, with EN 0, FR 1, DE 2, IT 3, ES 4, and
  99 for not set yet. `struct SaveData` has one more byte, which shifts the fields after it.
- **Per-language assets almost everywhere.** This covers the board graphics and HUD, mode
  banners, catch/evolution/shop texts, bonus field results, high score screen, title screen
  menus, options, pause menu, Pokédex, e-Reader screens and intro texts. The languages are
  grouped differently from asset to asset. For example, one table may be shared by
  English/French while German, Italian and Spanish each have their own; the code follows the
  grouping of the original ROM.
- **Pokémon names in three versions:** English (also used in Italian and Spanish), French and
  German.
- **The Pokédex** has its 205 entries (categories and descriptions) in five languages, with new
  glyphs (accented letters, ß, „ “ « », œ) and per-language character widths.
- **The ROM is 16 MiB** instead of 8 MiB.

## How the port is organized

### Code

- European code paths are written with `#ifdef EUROPE` (184 blocks in 28 source files).
- Per-language symbols use suffixes such as `_En`, `_Fr`, `_De`, `_It`, `_Es`, or a language
  group (`_EnFr`, `_EnDe`, `_EnDeItEs`, …).
- Macros in `include/global.h` (`LANG5_SWITCH`, `DMA_LANG5`, `EXTERN_LANG5`, `DMA_LANG4_ENFR`,
  `LANG4_SWITCH_ENDE`, `DMA_PORTRAIT_ANIM_FRAME`, …) express the usual "pick the asset of the
  current language" patterns, so that they compile like the original code.
- European RAM layout: `sym_ewram_eu.txt` (generated by `gen_ram.py`), `sym_bss_eu.txt` and
  `sym_common_eu.txt`.

### Data

- **`data/eu/*.s` are generated** by `tools/eu_port/regen.sh`. The US data sources are aligned
  against the European ROM: every US item found in the EU ROM is emitted from its US source, at
  its EU address. The European-only data in between is emitted as source:
  - symbolic pointer tables;
  - sprite sets with the `packed_sprite_oam(l)` macros, including the 556 European-only ones;
  - tables written with the element type of their C declaration;
  - VRAM destinations written with the same expressions as the US tables
    (`BG_ADDR_FOR_BOARD_WRAP(y, x)`, …).
- **`data/eu/src/*.inc`** hold the hand-written or dumped European sources:
  - the Pokédex entries in five languages;
  - the bonus summary texts;
  - the e-Reader texts (15 pages × 3 lines × 5 languages) and their page tables;
  - the default high scores, pause menu sprite offsets and "press start" tiles;
  - a few orphaned sound effect tracks.
- **Graphics.** 1,259 European graphics blocks were converted to per-language copies of the US
  files (`graphics/**/<US file>_<language>.png/.pal/.bin`), plus the graphics that exist only in
  the European version (language selection screen, rank ordinals, e-Reader texts, shop sign
  labels, the "!" letter of the board alphabet, …). About 2,300 PNG files were added. Each one is
  checked by converting it back to the exact original bytes. Special build rules are in
  `graphics_rules_eu.mk` and in gfx-config JSON files (for example, the French, German and
  Spanish Pokédex sprite sheets have their own segments in `graphics/pokedex/pokedex_gfx_eu.json`).
- Copies of English data that the European code never uses (EVO/coin arrows for French, Italian
  and Spanish) are built from the US files, and labelled as unused.

### Text encoding (`tools/preproc`)

- `.dexLang EN|FR|DE|IT|ES` selects the European glyph encoding of the Pokédex font for the
  strings that follow (`.dexLang US` is the original encoding).
- `{XXXX}` writes a raw glyph code, for the few characters drawn with an unusual width.
- `.dexCategoryLeftAligned` writes a left-aligned Pokédex category. This is used in French,
  German, Italian and Spanish; English keeps the US right alignment.
- With a `.dexLang` language set, `.ereaderText` writes the 25-cell lines of the European e-Reader
  screens. The new `.ereaderDexText` writes a line with the character widths of the Pokédex font
  of that language; the European lines use one or the other.

### Tools (`tools/eu_port`, Python 3 + pyelftools + capstone)

- `regen.sh` regenerates the European data in four steps:
  1. `codesyms.py` collects the symbols referenced by the code;
  2. `align_data.py` aligns the US and EU data;
  3. `gen_ram.py` writes the RAM layout;
  4. `gen_eu_data.py` writes `data/eu/*.s`.
- `gfx_eu.py` converts the European graphics to source files, with `gbagfx`, and verifies them.
- `dump_dex_eu.py`, `dump_ereader_eu.py` and `dump_tables_eu.py` write the files of
  `data/eu/src` from the European ROM.
- `check.sh`, `fdiff.py`, `nonmatching.sh`, `eudis.py`, `xref.py`, `langsw.py`, `romdiff.py` and
  `worddiff.py` compare functions and data with the European ROM.
- `lcm_sim.py` simulates agbcc's partial redundancy elimination, to understand why a value is
  reloaded or reused.
- `CLAUDE.md` holds the detailed working notes of the port, in Italian.

## Matching notes

Some European functions needed more than translating the logic. The causes are useful for other
agbcc projects:

- **`UpdateSapphireHatchMachine`.** In the European code the banner setup sits inside a
  `do { } while (0)`. The loop end note closes the CSE extended block, which changes the code
  after it (macros `BANNER_SETUP_BEGIN/END`).
- **`LoadTitlescreenGraphics`.** As in the US version, the palette, button icon and options
  sprite copies are repeated at the end of both branches of the saved-game test. The compiler
  merges the identical tails (cross jumping), and the duplication changes the register
  allocation of the code after them. decomp-permuter found an equivalent fake match (an
  if/else with two identical branches), which pointed to this structure.
- **`RestoreMainFieldDynamicGraphics`.** The egg frame index is read into a variable before its
  DMA copy, like the other copies of the function. The last difference was the reload register
  of one case: reload picks spill registers in rotation, and instructions that reload deletes
  later still move the rotation forward. A no-op `game->evoChainPosition += 0` at the end of the
  previous case gives the original registers. It is the same kind of fake match as the
  `gCurrentPinballGame->ball += 0` already present in the US code, and it is marked as such.
  It was found with decomp-permuter.
- **`EndOfBallBonusSummary`** was rewritten for the European language index, glyphs and tables.
  **`Draw{Ruby,Sapphire}ModeTimerDisplay`** use a per-language size for one block of "saver"
  tiles.

## Remaining work

- Find the original construct behind the fake match in `RestoreMainFieldDynamicGraphics`.
- Name and type the last 686 bytes of `.byte` data in `data/eu/rom_2.s`: small tables without a
  C declaration, and the broken end of an unused data copy.
- The 16 KB block at `0x08FE0000` looks like a development tool linked to run at `0x09FE0000`:
  an ARM entry stub that calls Thumb code, and accesses to IWRAM and `WAITCNT`. Without symbols,
  it is kept as bytes in `data/eu/rom_tail.s`.
- The US source writes the unused copies of the sprite data (`gSpriteSetRawDup_*`,
  `gPackedOamDup_*`, `gUnusedSpriteSets_*`) as sprite sets. They are actually sprite sets
  followed by animations (a frame count, then frame/duration pairs), as they are now written in
  the European data.

## History

1. **Matching build.** Every subsystem was ported in turn: language selection, Pokédex,
   e-Reader, field select, intro, title screen, high scores, options, banners, board
   indicators, shops, evolution mode, bonus fields, pause menu, save/restore and others. The
   European data was aligned against the US sources, until the first byte-identical European
   build. At that point, a few functions still used the original assembly and most
   European-only data was binary.
2. **Source conversion.** The remaining functions were decompiled to C, and the European data
   was turned into source: per-language graphics, the Pokédex and e-Reader texts, tables,
   sprite sets and symbolic pointers. The two last functions were matched with the help of
   [decomp-permuter](https://github.com/simonlindholm/decomp-permuter).

This work builds on the [pret/pokepinballrs](https://github.com/pret/pokepinballrs) disassembly
of the US version.
